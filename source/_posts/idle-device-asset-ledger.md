长假结束回到工位，抽屉里通常会多出几台设备：某个项目结项后留下的测试手机、买回来验证一版系统就再没开过机的平板、屏幕有划痕但不影响使用的备用笔记本。个人层面的"吃灰"只是浪费，企业层面的"吃灰"会变成三类具体麻烦：需要时找不到、找到时不敢用、处置时说不清上面有没有留过数据。

研发和测试团队的设备之所以比其他资产更容易失控，原因不在人的习惯，而在取得方式。生产电脑走 IT 采购流程，装 MDM、有编号、有归还节点；测试设备大多跟着项目预算走，项目组自己买、自己发、自己收，采购流程结束时台账流程也同时结束。要治的不是"人不负责"，而是这条断掉的记录链。

![闲置测试设备的登记、领用、巡检与退出四步台账](/images/posts/idle-device-asset-ledger.png)

## 一、先承认设备台账和固定资产台账不是一张表

财务要的是资产原值、折旧年限、归属部门；测试团队要的是"这台机器现在能不能装某个系统版本跑某个用例"。这两个诉求共用一张表时会互相牵制：财务字段要求稳定，工程字段要求频繁更新。我们见过的可行做法是分开主从——固定资产编号由行政侧维护，测试设备台账挂在它下面，只补工程关心的字段，两边用唯一编号关联，谁也不覆盖谁。

台账的目标要写清楚：它不是为了监督谁拿了设备，而是为了让补货和淘汰有数字可讲。这个定位决定了字段设计——每个字段都要在盘点、借用、处置、采购这四个动作里的至少一处被读到；读不到的字段最终一定是空的。

## 二、登记：字段要能被后面的动作复用

登记这一步最常见的失败是字段太少（只有一台机器的名字和买入价），或者字段太多（十几列，三个月后没人填）。最小集合是七类信息，且每一项都能回答后面的问题。

| 字段 | 用途 | 谁维护 | 写错的后果 |
| --- | --- | --- | --- |
| 唯一编号 | 借用、巡检、擦除、处置全部靠它串起来 | 登记人一次写定 | 编号复用等于历史记录断裂，报废时对不上 |
| 当前责任人 | 出问题找谁、超期找谁 | 随借用单自动变更 | 只在建表时填一次，之后所有催还未有对象 |
| 用途标签 | 项目专用 / 通用池 / 故障留样 / 待处置 | 项目负责人 | 分不出哪些能借给别人，只能全按"有人拿走了"处理 |
| 机型与系统版本、可升级上限 | 覆盖矩阵算缺口 | 巡检脚本回填 | 采购时说不清缺哪一档，只能按人头补 |
| 是否装过客户或内部敏感数据 | 决定是否必须走擦除与证明流程 | 领用人声明，巡检复核 | 送修、转手时最直接的合规风险点 |
| 购入批次与保修状态 | 报损走保修还是自费 | 资产管理员 | 过保机被送出去，来回物流加等待 |
| 最后心跳时间与地点 | 闲置判定、丢失排查 | 开机自检脚本自动写 | 人工填写不可能可信，只能自动化 |

前六个字段是静态或半静态的，第七个必须是设备自己上报的。把它和登记放同一张表的目的是让"这台存在吗"和"这台还在动吗"两个问题一次问完。

## 三、领用与巡检：一张借用单，一段开机自检

领用环节要解决的唯一问题是"责任随单走"。借用单最少包含：编号、领用人、起止日期、用途、归还条件（系统版本恢复、外观完好、数据已清）。规则要写到具体：跨项目转借必须重新建单，不允许"我跟他说了先给他用"；超期不自动续，需要显式确认；用途标签从"项目专用"改为"通用池"是一次变更，要有记录。这一条听起来官僚，但设备出问题时的追溯全靠它。

巡检不要设计成"每季度人工点一遍"，那种动作坚持不过两次。可行的形态是被动上报：设备开机时执行一段一次性脚本，把编号、系统版本、网络来源、时间戳发给收集端，脚本不常驻、不后台轮询。

```sh
# 放在设备开机自启里，一次上报即退出
DEV_ID=TST-0037                       # 台账里的唯一编号，写死在设备侧
os=$(uname -sr 2>/dev/null)           # 其他系统换成各自的版本查询命令
hb=$(date -u +%FT%TZ)
curl -fsS -m 5 -X POST https://asset.internal.example/hb \
  -H 'Content-Type: application/json' \
  -d "{\"id\":\"$DEV_ID\",\"os\":\"$os\",\"ts\":\"$hb\"}" || true
```

`|| true` 是必需的：收集端不可达时不能把设备开机流程卡住。对无法装脚本的设备（feature phone、部分平板、开发板），退化为"插上充电即视为一次心跳"的抽检方式，在表里明确标注这台的心跳来源，别让两类数据混在一个口径下比较。巡检的另一半是可用性抽检：随机抽几台要求现场安装指定系统版本并跑一条固定用例，能开机但装不上目标版本的机器，在台账上不该记成"可用"。

## 四、闲置的判定口径要在盘点之前定下来

盘点变成争论，几乎都是因为没提前定义"什么算闲置"。至少要把四类分开写清。

1. 长期无领用：连续超过约定天数没有任何借用单记录。这类最直观，也最容易和"项目间歇期"混淆，需要结合用途标签判断。
2. 领用了但从没开机：借用单存在，心跳记录缺失。这类要么是被拿去当备用抽屉机，要么是领用人根本不需要它。
3. 只出现在一个人手上：设备可分配，但借用记录始终是同一个人，无法交叉验证可用性。名义上是公用设备，实际是个人物品。
4. 借出超期未还：催还未响应的部分要在盘点报告里单列，不要和"闲置"混在一起，前者是流程问题，后者是配置问题。
5. 已进入退出流程却没实际交回：状态标成待处置、机器还在某个人的工位抽屉里。这一类既占台账又阻塞处置批次，判定要连着"收回时限"一起写。

判定口径要连着处置动作一起定，否则会得出"闲置 N 台"却没人负责消化。我们的写法是每条口径对应一个明确后续：转通用池、退还库存、发起采购需求、限期收回、或者进入退出流程。天数值按团队节奏定，定完写进台账说明页，不要在盘点当次临时协商。

## 五、退出：擦除要有可留痕的证明

设备的生命周期终点有三个：报损、内部降级使用、对外处置（转售、折价、退换）。风险最高的是"装过客户数据的机器走了后两条路"。要处理的层次比一次恢复出厂多：账号锁（厂商账号、MDM 描述文件、企业配置）不解绑，机器到了下家变砖，回收方也会拒收；加密没有落盘或密钥仍在旧账户下，恢复出厂并不能让数据不可读。

流程上我们分成三档：从未装过敏感数据的设备走普通回收；装过敏感数据但未落到客户实体的，执行擦除并保留执行记录（谁、哪台、用的什么方式、结果）；明确接触过客户业务数据的，擦除必须有第三方或独立见证留痕，且记录与设备编号绑定，保存期限跟合同要求一致。送修同样要过这一档判定——维修方可能接触到本地数据，不能因为"只是换屏幕"就跳过。

报损要有最低限度的判断依据：无法开机、屏幕破裂到影响读数、电池鼓包。电池鼓包单独标注，它既是处置限制也是安全限制，不该和其他坏机混在一个箱子里等处理。

## 六、洹拓视角：台账真正的产物是采购依据

四步走完，台账的产出不是那张表本身，而是两类可用于决策的记录：借用等待时长和覆盖缺口分布。前者回答"下一批要买什么"——把每次提出借用需求到实际拿到设备的间隔按机型、系统版本分组看，等待时间长的档位就是缺口；后者回答"该不该买"——把当前真机覆盖矩阵（需要验证的机型与系统版本组合）和台账里可用设备做差，缺哪补哪。

这两类数字比"每人一台"更省，因为它把设备发放的依据从人头换成了覆盖需求。同时它也避免了另一个常见错误：采购时按最贵或最常见的档位补货，结果补出来的机器没有覆盖任何一个未验证的组合，新设备很快也变成抽屉里那一台。

如果要给这套东西一个起步顺序，我们建议不要先上系统。四件事按这个次序做就能起步：把字段表建成一张共享表；给每台在用的设备贴一张带编号的二维码，扫码打开的就是借用登记页；把开机上报脚本发到能发的那部分设备上，剩下的先手工记；闲置判定口径写成半页说明放进表格里第一行。等这套流程跑顺、字段有真实数据被读到，再考虑和 IT 资产系统或工单系统对接——先有系统后补数据，是这类台账最常见的死法。

台账不是为了管人。它的意义是让下一轮采购、淘汰和处置有数字可讲，而不是让每台吃灰的机器都变成一次临时争论。
