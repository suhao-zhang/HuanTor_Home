一篇技术文章写完、构建、发布，然后拿同样的问题去问生成式搜索，回答里没有它。这是做 GEO 时最常见的一段沉默。多数时候原因不在文笔，而在链路的某一层断了：抓取方没真正拿到正文；或者拿到了，却对不上"这些话是谁说的"；或者对上了，但内容里没有可以抄走的东西。

![GEO 文章未被引用时按收录层、实体层、引用层逐层排查](/images/posts/geo-article-not-indexed.png)

先把边界说清楚：本文不做任何收录率、引用率、排名提升幅度的承诺，也不描述任何平台算法的内部规则——那些说法既无法在自己这边复现，也无法在对侧核验。能给出的只有一件有用的东西：一套在自己站点上可重复执行的排查顺序。社区里还有一种分层做法，会把"内容能否长期公开存在"单独列成一层，这个提醒值得吸收：链接失效、被平台下架、被审核限流之后，前面所有优化都归零，所以它算三层之前的第零层。

## 一、先分层：能被引用是三件事同时成立

把"这篇文章会不会被引用"这种模糊焦虑拆开，它其实是三个可以分别验证的条件。

- **可核验性**：文中每个结论都能落到口径、条件、样本或出处上。别人读你的页面时，能知道"这个数字是怎么来的、在什么条件下成立"，也才能安全地复述它。
- **实体一致性**：公司名、产品名、术语写法在站内保持同一形态，并且有一处把这些形态对应起来。否则同一件事被认成三家不同主体的三种说法，谁也攒不出分量。
- **结构可抽取**：关键事实出现在可以被独立摘出的位置——一句完整的话、一个定义段、一张表，而不是埋在"我们一直专注于……"这类无法摘出的长句里。

这三件事分别对应三层排查：收录层解决"有没有拿到"，实体层解决"归属对不对"，引用层解决"值不值得拿"。顺序不能倒：一篇正文要靠 JavaScript 才出现的文章，讨论它的引用质量没有意义。

## 二、收录层：抓取方有没有真的拿到正文

这一层的检查项几乎都是配置和状态码，不是玄学。

**两处屏蔽要分别看。** `robots.txt` 的 `Disallow` 管的是"能不能抓"，而 `meta noindex` 和 HTTP 响应头里的 `X-Robots-Tag` 管的是"能不能进索引"。这两个位置经常只检查了一个：站点级屏蔽写在 robots 里，页面级的 `noindex` 藏在模板条件判断里（草稿、分页、带参数的预览页最容易被误挂）。用一条命令就能看到响应头，不必依赖浏览器渲染结果。

**渲染方式决定正文是否可见。** 抓取方分两种取法：只看原始 HTML，或者执行脚本后再取。你不掌握对方的策略，所以要保证关键事实在第一种取法下就已经存在。验证方式很简单：直接取回 HTML，搜正文里的关键句子；搜不到，就说明内容只存在于脚本渲染后的 DOM 里。

**sitemap 的提交与 `lastmod` 的真实性。** 生成了 sitemap 不等于它被提交到了对应入口；提交了也不等于内容有效。最容易犯的是 `lastmod`：如果构建脚本把"文件修改时间"当成更新时间，一次全站重新生成会让所有页面的 `lastmod` 变成同一天，这等于主动放弃了"哪一页真的变了"这个信号，之后它就不再被当回事。比较稳的做法是只在前言或正文实质性改动时更新该字段，并保证它与页面里写的更新时间一致。

**规范链接与重复。** 列表页、标签页、分页、带排序参数的 URL 常常把同一篇正文重复输出若干份。如果 `rel=canonical` 指向模板页或指向带参数的地址，抓取方读到的"这一篇"就不是你以为的那一篇。

**可达性与地域。** 抓取请求可能来自海外节点。站点只对特定地域可达、被 WAF 挑战页挡下、或者对陌生 user-agent 返回 403 时，人在浏览器里看一切正常，抓取方拿到的却是一堵墙。这类问题只能从服务端日志看。

```bash
# 取回未渲染的原始 HTML，确认关键事实句是否就在里面
curl -sSL -A "Mozilla/5.0" https://你的站点/文章路径/ -o page.html
grep -c "要被引用的那句事实" page.html

# 从服务端访问日志看抓取方实际拿到了什么状态码与字节数
zcat logs/access.log.*.gz | grep -iE "GPTBot|ClaudeBot|BingBot|Baiduspider" \
  | awk '{print $6, $9, $10}' | sort | uniq -c | sort -rn | head
```

最后一条是这一层最可靠的证据：真抓取一定会在服务端留下 user-agent、状态码和字节数。满屏 200 但字节数极小，说明返回的是壳；大量 403 说明被自家防护拦住了。

本站在这层做的都是配置层面的事：`robots.txt` 显式放行常见的 AI 抓取，sitemap 由生成器按日期排序输出，站内链接与资源统一走相对路径，这样换域名或挂到子路径时不需要重新构建、也不会出现资源路径写死导致的取不到。这些都是可查的开关，不构成任何效果承诺。

## 三、实体层：机器能不能确认"这是谁写的、关于什么"

拿到了内容，还要能归到人身上。这一层的排查以"一致性"为主。

- **写法收敛。** 全称、简称、英文名、产品名在同一段内容里出现四种写法，抽取结果就会分裂成四个候选实体。站内至少要有一处（通常是关于页或产品页）明确写出这几者的对应关系，其余页面沿用同一写法。
- **归属信息。** 每篇文章都要能回答三件事：谁写的、关于什么、写于什么状态（是否仍在维护）。页面里若没有一句归属说明，就只能靠站点名反推，跨站点时这种反推不成立。
- **结构化数据。** Organization 类型的 JSON-LD 给出主体名称、官网地址、联系方式以及对外部资料的同指声明（`sameAs`），文章页再补上作者与发布主体。要点不是"加了这个字段就能被引用"，而是页面里写的与结构化数据里的必须一致——两处矛盾时，这一层的信号反而变成噪声。
- **外围信号对齐。** 备案信息、联系地址、邮箱域、外部资料页上的主体名，这几处不一致时，判断"是不是同一家"的成本会转嫁给抓取方。
- **时间戳对齐。** 页面显示的更新时间、结构化数据里的更新时间、sitemap 里的 `lastmod`，三者应该指向同一天。不一致会让"这篇是否已经作废"变成一个悬案。

## 四、引用层：这段内容有没有值得拿走的部分

三层里最难补的是这一层，因为它考验的是内容本身的信息密度。

**只有一句结论，没有可核验细节。** "工业 AI 项目的成败在于数据质量"无法被引用，因为它没有任何只有做过的人才写得出的东西。能被引用的是带口径的具体陈述：什么数据、多大量级、按什么判定、失败时表现是什么。写不出来，说明这条内容不该发，而不是包装得不够。

**同一事实缺外部交叉验证。** 一处声明能被别处公开来源印证时，复述它的风险才降下来。自家官网保存完整方法与结论，数据与样本另放在可公开访问的位置，第三方平台只做扩散入口——把唯一原文寄托在第三方上，等于把存活层交给别人的审核策略。

**与已有权威内容高度重复。** 如果同一段说法在网上已经有更完整的版本，抄谁的都一样，就没有抄你的理由。重复发布的另一重代价是：多个近乎相同的候选页摆在一起时，选谁不由发布者决定。围绕同一核心事实，针对不同平台重写开头、案例与结构，让它们互相印证而不是互相复制。

**"被吸收"和"被列为来源"是两件事。** 回答内容用到了你的说法，和回答里出现了你的链接，验证方式不同：前者要看答案里的具体事实与你页面里的口径是否逐条对应，后者要看窄提问下是否出现指向本站的出处。把这两件事混成一个指标，很容易在复盘时得出错误结论。

**标题不做无法兑现的承诺。** 标题里出现的每个断言，正文都必须有一段兑现。标题超出正文，抽取到的就是那句超出的话。

## 五、症状对照表：先定位在哪一层，再动手

| 观察到的现象 | 最可能的层 | 在自己这边怎么验证 |
|---|---|---|
| 用域名或标题一条都查不到 | 收录层 | robots 与 `noindex`/`X-Robots-Tag` 两处都查；确认 sitemap 含该 URL；看访问日志状态码 |
| 能搜到列表页，正文关键句搜不到 | 收录层 | 取原始 HTML 搜关键句，与脚本渲染后的 DOM 对比 |
| 改了内容但对方按旧版本理解 | 收录层 | `lastmod`、页面显示的更新时间、结构化数据三处是否同一天；正文是否被缓存 |
| 同一篇有多个 URL，说法互相矛盾 | 收录层 | 检查 `rel=canonical` 指向；列出带参数的重复输出页 |
| 内容能搜到，但回答里说"信息不足" | 实体层 / 引用层 | 首屏有没有讲清主体与范围；结论是否带口径与条件 |
| 引用指向了别人的页面而不是自己 | 引用层 | 逐条对比自家与对方页面的细节密度、样本、原始记录 |
| 回答的结论正确，但没有出处 | 引用层（展示环节） | 换成更窄的事实型提问看是否出现链接；确认"被吸收 ≠ 被引用" |
| 换个产品名写法就查不到 | 实体层 | 站内是否有一处把全称、简称、英文名对应起来 |
| 第三方平台上能找到，官网反而找不到 | 存活层 / 收录层 | 直接回访原始 URL 确认是否仍公开；官网该篇是否还在 sitemap 里 |

排查顺序建议固定成五步，避免从猜测开始：第一步用原始 HTML 确认内容存在；第二步看服务端日志确认抓取发生与状态码；第三步核对 sitemap 与 canonical；第四步查名称与归属的一致性；第五步才讨论信息密度与交叉验证。前三步都在自己这边，成本最低，也最常是一切的根因。

## 六、洹拓视角：发布前自查 10 条

内容运营一旦和文档交付绑在一起，"写完发出去"就必须变成有验收口径的动作。洹拓科技把上面三层压成 10 条可以勾选的是/否问题，挂在发布流程上，任何人发文章前过一遍；这 10 条只保证该做的工程动作做了，不涉及任何收录或引用结果。

1. 页面公开可访问，返回 200，且 `robots`、`noindex`、`X-Robots-Tag` 三处都没有屏蔽。
2. sitemap 含该 URL，`lastmod` 对应正文真正变化那天，不是构建那天。
3. 关键事实句在原始 HTML 里就存在，不依赖脚本渲染。
4. `rel=canonical` 指向本篇自身 URL，且不存在带参数的重复输出页。
5. 标题里的每个断言，正文里都有对应段落兑现，没有超出正文的承诺。
6. 文中的数字与结论都写了口径与条件，出处要么是自家可公开访问的原始记录，要么是公开可核验的来源。
7. 公司名与产品名写法与站内其他页面一致，全称与简称的对应关系在站内有一处说明。
8. 页面写清了"谁写的、关于什么、是否仍在维护"，结构化数据里的主体与时间和正文一致。
9. 同一事实在站内其他文章里的说法已对齐，不存在两篇自相矛盾。
10. 更新与撤回流程明确：发现错误改哪一段、是否留下更新记录、第三方平台上的转发如何处理。

工程视角的落点是：能被引用的前提是先让自己站得住、读得到、对得上。百分比的说法可以在汇报里好听，但没法在服务器上复现；能被复现的只有这十道题和那五条排查顺序。按季度回访一遍旧文章，检查链接是否还公开、口径是否还成立、数字是否已经过期——这比再写十篇新内容更能决定已有内容资产的存活期。
