语音合成接口的选型讨论，通常从"哪家音色更自然"开始，然后停在"这家便宜一点"。真正在项目里踩坑的位置往往不在这两处：交互场景里用户抱怨"半天不出声"，测的是首包延迟；夜间批量任务跑不完，卡的是整段耗时与并发路数；上线后账单对不上，差的是计费口径里那几行小字。

![语音合成选型：首包延迟、发音纠正与计费口径的三条判断线](/images/posts/tts-api-selection-latency.png)

这篇把选型拆成可以各自验证的几块：两个时间指标的含义、延迟预算的构成、限流与配额的差别、发音纠正的能力边界、四种计费口径的换算方法。所有算例里的数字都是自设假设量，不涉及任何厂商报价——报价要按对方口径单独确认，把它抄进文章里只会误导。

## 一、两个指标别混：首包延迟与整段合成耗时

**首包延迟**决定"开口快不快"：从请求发出到拿到第一段可解码音频的时间。**整段耗时**决定"这一整篇能不能一次做完"：从请求发出到最后一个音频字节到达的时间。在非流式接口下，两者是同一个值——必须等全文合成完毕才有响应，首包等于整段。只有在流式（分块下发）接口下它们才分离，而分离之后含义完全不同。

对流式接口还要再拆一层，报数时不说清就会吵架：

- `t0` 请求发出。要写明连接是否已建立：从零开始建连（DNS + TCP + TLS）与复用长连接，差值可以远大于服务端本身。
- `t1` 收到第一段可解码音频。
- `t2` 播放器真正出声，等于 `t1` 加客户端解码与缓冲阈值。用户感知的是 `t2`，SLA 常写的是 `t1`，两者中间的缓冲策略必须显式记录。

两个指标各自对应的场景要分清。语音助手、电话客服、实时播报关心 `t2`；有声读物、课件批量导出、告警录音归档关心整段耗时和单路吞吐，首包反而是最不重要的那个数。用一句话文本去压测首包、然后据此判断"能不能承接夜间一万篇合成"，是用错了指标。

服务端首次下发之前需要凑够一个文本边界，这一点很关键：多数流式实现按句子切分，遇到句末标点才成块合成。如果输入是一段两百字没有句号的长文，首包必然晚，而这是文本切分问题，不是模型慢。

## 二、延迟预算拆开：哪些能压、哪些压不动

把 `t2` 拆成环节列表，才知道优化该找谁。

| 环节 | 构成 | 能否自己压 | 压法与副作用 |
|---|---|---|---|
| 建连 | DNS、TCP、TLS 握手 | 能 | 长连接与会话复用；代价是连接池管理与鉴权过期处理 |
| 网络传输 | 往返时延、出口带宽排队 | 有限 | 就近接入点；跨地域部署才有效，客户端优化压不动物理时延 |
| 服务排队 | 超出并发后在队列里等 | 不能（只能加配额或削峰） | 客户端限并发排队反而把等待搬到本地，`t1` 只会更差 |
| 文本前端 | 数字与单位展开、分词、注音、韵律 | 半能 | 客户端预先分句、控制首句长度；切得过碎会破坏韵律、跨句指代丢失 |
| 声学与声码 | 模型推理、采样率、每块音频时长 | 不能 | 属对方规格，通常只有换版本或换音色档 |
| 编码与分块 | 音频容器头、首帧长度 | 能（选格式） | 容器头与首帧会推迟"可解码"时刻；高压缩格式省带宽但费客户端 CPU |
| 客户端缓冲 | 起播阈值、抗抖动缓冲 | 能 | 缓冲小则起播快但易卡顿，网络抖动时先听到断续 |

从这张表能得出一条实用结论：可控项集中在建连、文本切分、格式选择与缓冲策略；服务端的推理与排队不可压缩，只能通过配额解决。因此"把首包做小"的正确顺序是先确认自己是不是在排队（看限流命中），再检查首句长度，最后才谈网络路径。跳过前两步去做 CDN 或换服务商，多半白干。

## 三、限流与配额：为什么压测阶段先炸的是配额

接口文档里的限制通常有三种，含义互不替代。

- **QPS**：单位时间请求数，瞬时约束。
- **并发路数**：同时在处理的合成会话数，与请求频率无关——长文本低频也可能把并发打满。
- **字符配额**：按日或按月累计的合成字符量，累计约束。

压测时最先撞上的往往是配额而不是 QPS。原因是压测的单位时间文本消耗远高于真实业务：把并发拉满跑半小时，消耗的可能是一整天正常业务的量，日累计配额于是被吃穿。撞上之后表现是限流响应，如果你把限流与重试混在延迟统计里，会得到一份"P95 很难看但原因不明"的报告。

正确的做法有三条。第一，压测前确认配额是否可临时提升，或把压测流量与生产流量隔离在各自独立的密钥下，避免压测把生产额度耗光。第二，日志里把"被限流"与"合成慢"分成两类统计，分别报告：前者算命中比例与退避时长，后者才算延迟分布。第三，验证退避行为是否真的按文档执行——包括是否指数退避、是否尊重响应头里的重试间隔、失败请求是否也计入配额（这条经常被忽略，一旦重试风暴就会让配额崩得更快）。

顺带确认单次请求长度上限与超长文本的处理方式：是直接报错、静默截断，还是自动分片。静默截断在有声文档场景里等于内容缺失，属于最难被发现的一类事故。

## 四、发音纠正：SSML 与词典能做到哪一步，做不到时怎么办

合成质量的事故集中在五个位置，音色再好也躲不开。

**多音字。** "行""重""参""得"这类字的读音由上下文决定，靠模型判别的错误率不可能为零，而业务里出错的就是那几个高频词（"银行/行家""重量/重新""参数/参加"）。**数字与单位。** 千分位、区间、比分、量级单位（千伏、兆瓦）、百分号、摄氏度、`km/h` 这类符号，读法分歧最大。**时间与日期。** 时刻、时长、ISO 形式的日期串、"几点到几点"的区间，读法在不同场景下不一致。**专有名词。** 公司名、产品型号、项目代号、人名里的生僻字，模型默认读错，必须靠词表。**中英混排。** 缩写按字母读还是连读成词，词内切换是否自然，是混排文本最常见的听感问题。

能力边界要按这几条核对：接口是否支持标记语言（`phoneme` 音素替换、数字与单位类型的读法标注、`break` 停顿、`prosody` 语速音高）；如果支持，是全套还是子集；是否另有自定义发音词典，粒度是词级还是字级；词典作用域是全局还是绑某个音色；SSML 标签文本本身是否计费。这些答案只有对方文档和一次实测能给出，不能靠"应该都支持吧"来定架构。

标记语言和词典都覆盖不了时，才走文本层预处理，并且要做成可管理的形态：显示文本与朗读文本分离成两个字段，中间用一张"朗读改写表"（原文片段到朗读片段的映射）转换；这张表要版本化、可回归，出现"念错"时能定位到具体条目，而不是散落在业务代码里的字符串替换。预处理还有一个约束：必须可逆或有对账手段，否则朗读出去的一句话，很难证明它和页面上那句是同一个意思。

判定"够用"的方法也很直接：拿自己业务里的真实语料，按上面五类各凑一批高危词，逐条听。高危词表要长期维护，它是发音验收的基线，音色或版本一换就要重跑。

## 五、计费口径：同一份业务量分别算四遍

| 计费方式 | 计费单位 | 必须问清的细节 | 更适合的调用形态 |
|---|---|---|---|
| 按字符 | 输入文本字符数 | 一个汉字算 1 还是 2；标点、空白、换行是否计入；标记语言标签是否计费；失败请求是否计费 | 短文本、高频、内容长度稳定 |
| 按音频时长 | 输出秒或分钟 | 向上取整粒度；不同码率与采样率是否同价；试听与重试是否重复计 | 长文本、有声内容、时长可控 |
| 按调用次数 | 每次请求 | 自动分片算 1 次还是 N 次；重试是否算新调用 | 请求粒度可控、单次内容偏长 |
| 按并发或规格包月 | 路数或规格 × 时长 | 并发路数如何界定（同时在处理即算）；超额请求是被拒还是排队；包月未用完是否结转 | 有明确吞吐窗口、可预先削峰 |

四种口径要拿同一份业务量各算一遍才有可比性，单价留成符号，不要抄别人的数字。下面这组量级是本文自设的假设，只用来演示公式，不代表任何真实报价或真实客户数据。

```python
# 全部为假设量：仅演示四种口径的换算方法
CHARS_PER_MONTH = 1_000_000     # 假设月合成文本总量（字）
CHARS_PER_REQUEST = 250         # 假设平均单次请求长度（字）
SECONDS_PER_CHAR = 1 / 4        # 假设朗读速率：4 字/秒
RTF = 0.3                       # 假设单路实时率：合成 1 秒音频耗 0.3 秒

req_count = CHARS_PER_MONTH // CHARS_PER_REQUEST          # 4_000 次
audio_sec = CHARS_PER_MONTH * SECONDS_PER_CHAR            # 250_000 秒音频

# 最坏窗口：假设 2_400 次请求由夜间批处理在 300 秒内下发
BURST_REQ, BURST_WINDOW_SEC = 2_400, 300
burst_audio_sec = BURST_REQ * CHARS_PER_REQUEST * SECONDS_PER_CHAR   # 150_000 秒
need_lanes = burst_audio_sec * RTF / BURST_WINDOW_SEC                # 150 路

print("月请求数", req_count, "月音频秒", audio_sec)
print("最坏窗口需要的并发路数", round(need_lanes))
print("四种口径的量：字符", CHARS_PER_MONTH, "音频秒", audio_sec,
      "请求次数", req_count, "并发路数", round(need_lanes))
```

假设量代进去的结果是：月请求 4,000 次、月音频约 250,000 秒（约 69 小时）；如果最坏窗口成立，那个窗口需要约 150 路并发，只买 20 路就会把任务排到窗口外，第二天早上还没跑完。到这里就停住：把四种口径的"量"算清楚，各自乘上对方给的单价才是可比的账单。跳过这一步直接比"哪家便宜"，很容易比错——按字符计费的接口对长文本有利，按音频时长计费的接口对慢速朗读不利，而你的业务量分布才是决定因素。

## 六、验收清单与洹拓视角

**音色与克隆的合规线。** 使用真人音色要有可留存的授权记录，声音克隆要能证明授权范围与用途；留痕不是形式，是出现争议时唯一能拿出来的东西。音色要能下线：供应商弃用某个音色时，业务侧必须有一次性的音色重映射和回归测试，而不是让线上播报突然换成另一个人的声音。合成内容对外发布时按生成合成内容标识的相关规定处理，标识字段要留在产物元数据里，而不只是写在一页说明里。

**端侧兜底什么时候必须做。** 三类场景绕不开：终端在弱网或无网环境（外勤、车载、应急播报）；文本不能出内网（涉密或内部资料朗读）；供应商不可用时的最小可用集。代价也要算清——端侧音色的自然度通常与云端不在同一档，多端音色不一致会造成品牌听感分裂，端侧还带来包体积与许可问题。务实的组合是：云端主路 + 端侧保底音色，并且保底路径也要过发音验收。

上线前的验收清单，按这 9 条执行，每条都要留下可回放的原始记录：

1. 固定语料集就位：包含首句长度分布、多音字高危词表、数字与单位用例、中英混排用例、空白与超长边界各若干条。
2. 首包延迟按短、中、长三档分别记录 P50 与 P95，并写明计时点定义（`t1` 还是 `t2`）。
3. 整段耗时与单路吞吐实测，用来推算夜间批处理窗口能承接的量。
4. 断句抽检：按随机样本加边界样本两部分，判定规则写清（句末标点、无标点长句、括号与引号嵌套）。
5. 发音人工听审：高危词逐条过，再按随机量听审，问题按多音字、数字、单位、专名、混排五类归档。
6. 异常行为验证：超时、限流、空白输入、超长文本、鉴权过期各有明确表现，并确认失败请求是否重复计费。
7. 重试幂等：重试带同一请求标识，退避策略与文档一致，不产生重复音频与重复账单条目。
8. 缓存策略：相同文本是否复用产物，命中与失效口径可查。
9. 日志字段完整：请求标识、文本长度、首包、总耗时、状态、音色标识与版本、计费口径——缺哪一项，将来就有一类问题查不动。

从洹拓科技做语音接入时复盘过的这些位置看，选型结论很少落在"哪家模型更强"上，而落在"哪家的口径能被我验证"上。首包定义能不能对齐、限流与配额能不能分开统计、发音问题能不能落到词表条目、四种计费口径能不能用自己真实的业务量算一遍——这四件事都能验证的接口，即便音色不是最讨喜的那个，上线后的事故也更少；任何一件验证不了的，谈什么都还太早。
