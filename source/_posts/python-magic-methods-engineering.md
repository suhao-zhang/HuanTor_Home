## 一、魔法方法的本质是"协议"

Python 的双下划线方法不是给语言内部用的私有能力，而是**对象向调用方声明自己支持哪些操作**的协议接口。`len(x)`、`x in y`、`with x:`、`print(x)` 这些日常写法，全部走协议而不是走具体类型判断。

这带来的实际差别是：**你写的类能不能被标准库、日志框架、序列化器和同事的代码"正常对待"。**

我们评审 Python 代码时，最常见的三类线上问题恰好都落在协议没实现上：

- 日志里出现 `<app.models.Order object at 0x7f8...>`，事故现场看不到任何有效信息；
- 把自定义对象放进 set 或 dict 键，**结果两条逻辑相同的数据被当成两个不同元素**；
- 对象传给 `json.dumps` 直接抛 `TypeError`，只能临时加一个 `default=str`，输出格式没人负责。

## 二、最小必要清单（我们团队按这条执行）

**1. `__repr__` 是强制项，且必须对排查有用。**

```python
def __repr__(self) -> str:
    return f"Order(id={self.id!r}, status={self.status!r}, amount={self.amount!r})"
```

约定：**`__repr__` 写给工程师看，`__str__` 写给用户看。** 只实现 `__repr__` 时，`str()` 会自动回退到它；反过来则不行。所以资源有限时，先做 `__repr__`。数据类用 `@dataclass` 自动生成，这也是我们推荐业务模型一律用 dataclass 的最实际理由——不是少写代码，是**保证每个模型都有可用的 repr**。

**2. 相等与哈希必须成对考虑。**

```python
def __eq__(self, other):
    if not isinstance(other, Order):
        return NotImplemented
    return self.id == other.id
```

关键规则：**一旦自定义 `__eq__` 而没有自定义 `__hash__`，Python 会把该类的 `__hash__` 置为 `None`，实例从此不可哈希**——放进 set、当 dict 键全部报错。这是典型的"改一处坏一片"。反过来，若两个对象 `__eq__` 为真，则它们的 `__hash__` 必须相等，否则集合行为将出现难以复现的丢失。

我们的判断标准很硬：**如果类的相等性语义是"按 id 相同"，那哈希就必须只用 id。** 两者混用可变字段，是缓存错乱的根源。

**3. 需要迭代或切片语义的容器，实现 `__len__` 与 `__getitem__`。** 这两个凑齐，就免费获得迭代、`in` 判断和切片。在加 `__iter__` 之前先想清楚这两件事——很多"自定义迭代器"其实不需要。

**4. 上下文资源用 `__enter__` / `__exit__`，别用 `__del__`。** 数据库连接、文件句柄、临时目录一律走 `with`。`__del__` 依赖 GC 时机，在异常路径和解释器退出阶段都可能不执行。

**5. 序列化边界自己承担。** 业务模型显式提供 `to_dict()`（或用 `dataclasses.asdict`），而不是在调用侧到处手写字段列表。协议缺失可以用方法补，**但必须有人负责。**

## 三、几个"看起来优雅、实际是坑"的用法

- **`__getattr__` 做动态属性代理。** 拼写错误不会报错，只会静默返回一个新对象，几层调用之后错误信息彻底失去线索。要实现的话，第一条就是**对不存在的名字抛 `AttributeError`，并在 docstring 里写明可返回什么。**
- **`__bool__` 与 `__len__` 语义冲突。** 只实现 `__len__` 时，空容器自动为 `False`。一旦加了 `__bool__` 返回 `True`，"对象存在但内容为空"和"有内容"在调用方看来就一样了。
- **运算符重载写非同类运算。** `Vector + int` 允许 int 隐式当标量，读代码的人要现场做心算。**协议是给人读的，不是为了少写一层转换。**

## 四、洹拓视角：为什么这条值得写进团队规范

我们做数据平台和大模型应用交付，Python 是主力语言。项目里的痛点很少是"不会用某个魔法方法"，而是**同一个仓库里三种模型风格并存**：有人用 dataclass，有人手写 `__init__`，有人用 dict 直接传。后果是：

1. 日志和异常堆栈里没有可用信息，排障靠现场复现；
2. 对象进缓存、进 set 的行为依赖实现细节，改一个字段就可能引入重复计数；
3. Code review 无法机械化，只能靠人肉看有没有漏字段。

我们的解决办法很笨但有效：**在脚手架里固定 `@dataclass` + 显式 `to_dict()`，然后用一条 CI 规则检查业务模型类是否实现了 `__repr__`。** 一行 lint 换掉一整类线上排查困难，这属于典型的低成本高回报。

对本地正在建 Python 团队的企业，这也是一种务实的起点：**规范先解决"可观测"，再解决"优雅"。**
