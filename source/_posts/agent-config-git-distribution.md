## 一、配置进了仓库，变更对象的性质就变了

据公开报道，有厂商开源了一款基于 Git 的团队 AI 协作工具，把团队在用的 Skill、工作规范、工具配置和项目知识收进同一个仓库，像管理代码一样做评审、更新和版本管理，再同步到成员各自使用的 Agent，一人配置、多人复用。这款产品的名称、同步协议、权限模型、冲突解决策略与内部实现，我们不做任何推断，也不评价它的设计优劣与选型取舍。值得单独拎出来的事实只有一句：配置从"每台机器上各有一份"变成"仓库里有一份"。

这句话换掉的是变更对象的性质。代码改错了，编译、测试、灰度这三道过滤器至少会拦住一道；配置改错了，一道都不会亮红灯，因为它在语法上完全合法，加载它的进程也不会报错。更麻烦的是爆炸半径按"人"计算：一次合并可能同时改变全团队智能体的行为，而这些成员正在跑的作业、正在提交的代码、正在给出的结论，都在这次合并之后换了口径。

这就是我们说的共享配置变更。它需要的是变更管理那套管法——谁改的、什么时候生效、影响了几个人几件事、出事怎么退。而 Git 仓库天生只给了代码那套管法：有历史、有评审、有回滚，但没有"生效"这个概念，也没有"受影响成员"这个维度。把这两套管法接起来，才是这类工具能否在项目组里长期活下来的关键，而不是仓库本身好不好用。

## 二、四类失效，各自的表现与各自的处置

第一类，本地同名配置遮蔽。成员机器上原先就有一份同名的 Skill 或规范文件，仓库下发的那份被就地盖住。表现是"改了没反应"：仓库合并记录清清楚楚，成员侧的会话行为一点没变，改动者以为已经生效，验收的人以为在测新版本。这类失效的处置不靠提醒，靠比对：把成员侧实际加载的配置摘要取回来，和仓库里目标版本的摘要做一致性快照比对，差异列表化。谁机器上有一份仓库外的同名文件，这件事必须是一个会被检出的状态，而不是一个只有本知道的隐藏事实。

第二类，同步滞后造成同团队双行为。仓库改了，下发有时间差，而成员不会整齐地在同一时刻刷新。于是同一团队在同一时刻跑着两种行为：两个人让同一个智能体做同一类任务，得到不同口径的产出。它的真正代价不在产出不同，而在会话归因失效——出问题时按会话时间倒查，找不到唯一的"当时生效的版本"，因为生效时间不是一个点而是一段重叠窗口。处置办法是把生效做成有明确边界的动作：给每次下发记一个生效时间，并且让任务与会话能带出它当时用的是哪个版本。

第三类，敏感内容顺手提交入仓。配置里最容易夹带三样东西：密钥与令牌、内部域名与端点、客户数据与真实案例片段。写规范的人为了说明清楚，把一段真实请求贴进去，评审的人只看措辞不看内容，就进去了。Git 历史不能靠删除文件清理，这是常识，但在配置仓库里几乎每天有人重新犯一次。处置只有前置一条路：入仓前的密钥与标识扫描门禁，加一条团队约定——仓库里的示例一律用构造值，真实值留在成员本机或密钥系统里，仓库只留字段名与获取方式。

第四类，未经评审的规范改动直接进入。一条提示措辞的改动，改的人只想要"顺手把口径拧一下"，没有评审、没有通知，合并之后全团队行为同时偏移。它和第一类的区别在于它"生效了"，所以更难发现：产出质量的变化会被当成模型状态波动，没人往一次提交上联想。处置办法是按配置类型强制评审档位，并且给规范类改动加一个最低门槛——哪怕只让一个人看过并署名。

## 三、四类配置分层，评审强度不该一样

洹拓把智能体配置按"改动会改变什么"分成四层，分层的唯一依据是后果类型，不是文件大小也不是目录结构。前三类改动会改变行为，知识类改动改变的是输出内容，这两类在事故定位上是完全不同的东西，评审强度自然不该一样。

| 层 | 内容 | 改动改变的 | 评审档位 | 生效方式 |
|---|---|---|---|---|
| 能力类 | Skill 清单、工具与允许的动作范围 | 智能体能做什么 | 双人，需说明新增动作的影响面 | 灰度，先小范围 |
| 规范类 | 提示词、工作约定、输出格式要求 | 智能体怎么做 | 至少一人署名评审 | 分批下发 |
| 环境类 | 模型标识、端点、超时与重试参数 | 成本、时延与可用性 | 变更单，需回滚值 | 即时，但需生效记录 |
| 知识类 | 项目文档、术语表、示例片段 | 输出内容本身 | 抽查复核即可 | 全量即时 |

能力类最该重审，因为它动的是权限边界：一个 Skill 的增减，等于给全团队智能体的可执行动作集合增删，而这类改动经常被写成"补了个小工具"。环境类改动本身简单，但它是唯一会立刻反映在账单和超时率上的，所以重点不在评审而在生效记录与回滚值。知识类可以宽松，但不能没有版本可追溯，因为客户投诉往往是"这个回答按哪版资料给的"。

一个反复出现的误区是把四层放在同一套规则下管：要么全部严格到没人愿意提改动，最后大家绕开仓库自己配；要么全部宽松，规范和能力类改动混在知识类提交里一起进去。我们的做法是让目录结构承载规则，四层各自有 CODEOWNERS 性质的归属人，评审档位由路径决定而不是由提交人自选。

## 四、下发三档，各自的适用面与观测点

全量即时同步最简单，也最危险。它适合知识类和低风险的环境类改动，特点是生效时间唯一、归因干净。观测点是同步任务的失败率与成员侧摘要一致性，不是"同步成功了"这个回执本身。

按角色分份是团队规模上来之后的必然选择。不同角色需要不同能力集合：做数据处理的智能体和做前端改动的智能体，工具清单本来就不该一样。它带来的新问题是一份配置的多版本共存——同一个人在不同项目里身份不同，仓库里就要有多份彼此独立的定义，任何"顺手合并成一份"的动作都会造成权限外溢。观测点是分份之间的重叠区域：哪些项在所有份里都一样，那些才是真正可以"一人配置多人复用"的部分。

分批灰度是行为类改动该走的通道。这里的困难是配置没有天然的"错误信号"，灰度期间看什么？我们看三样：改动前后同类任务的产出格式合格率、人工介入与推翻次数、以及成员侧上报的异常行为描述。这三样都不精确，但足以把"明显变差"从主观感受变成一个有人在盯的指标。灰度的另一价值是留出观察窗口，让第二类的双行为期在一个可控的小群体里发生，而不是全员同时撞上。

## 五、生效记录与回滚台账要留的字段

配置出事之后被问到的第一句话永远是"这次改动影响了谁、影响了几件事"。Git 历史回答不了，因为它知道提交，不知道生效。洹拓在给客户搭这类仓库时，要求每次下发至少留这几项：

- 配置项标识与所属层：能力、规范、环境、知识四层之一，用于反查评审档位是否被绕过
- 版本号与内容摘要：摘要用于和成员侧比对，光有提交号无法证明机器上跑的就是它
- 生效时间与生效窗口：下发开始到全员确认一致的时间段，重叠期内的会话要单独标注归因不确定
- 受影响成员清单与受影响作业：按人展开，再按人列出当时正在跑的任务
- 变更单标识与批准人：与代码评审记录分开，配置变更要能独立被追问
- 回滚值与回滚后的生效时间：回滚本身也是一次变更，同样要留生效记录，否则两次偏移会混在一起

回滚要特别说一句：配置的回滚不等于文件内容回退。成员侧可能有本地残留、有正在跑的会话、有已经按新口径产出的结果。回滚之后这三样不会自动复原，所以回滚记录里要带"需要重做的动作"一栏，而不只是一个 revert 提交。

## 六、验收四个动作与两份交付物

上线这套管法时，我们用四个动作做验收，不看文档写得全不全。一致性快照比对：随机抽成员侧的实际加载状态与仓库目标版本对账，差异必须为零或有已知解释。密钥扫描门禁：验证它真的能拦住，而不是只验证规则存在。评审覆盖率：按层统计，规范类与能力类要接近全量，知识类可以给区间。抽样复核两三个真实会话：从改动生效窗口里挑几个已完成会话，看它的实际行为口径落在改动前还是改动后——这个动作最土，但只有它能证明前三个动作没在自说自话。

交付物就两份，都是可以直接抄进流程的表。第一份是配置仓库分层与评审规则表，即上面那张四层表加上路径归属和评审档位，它决定谁必须看某次提交。第二份是配置下发与回滚台账字段表，即第五节那六项加"需要重做的动作"，它决定出问题之后能不能在十分钟内说清影响面。这两份表一旦落地，"一人配置多人复用"才是件省事的事；没落地，它只是把一个人的错误复制给了全团队。
