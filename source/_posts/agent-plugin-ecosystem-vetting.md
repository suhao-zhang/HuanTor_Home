## 一、审查对象变了：从能跑的代码到能替你行事的代码

据公开报道，一个开源智能体框架在代码托管平台上的 Star 数在很短时间内越过 25 万，跟着长出来的是一批民间开源插件。我们不拿这个数字做评价，它最多算热度信号。值得写下来的是另一件事：插件以这种速度增长时，团队被迫在几天之内回答"这个能不能进项目"，而手里的流程是按"库"设计的。

传统依赖审查那几道闸仍然有效——来源能否追溯、维护是否活跃、许可证是否可用、有没有已知漏洞记录、体积与传递依赖、构建产物能否复现。这些站内讲过，不重复。要补的原因在于主体性质变了：一个库拿到的是你显式传进去的参数，算完把结果还给你；一个插件在多数智能体框架里运行在同一个进程、同一个运行时上下文里，它看得见会话内容、文件路径、工具调用的入参，还能主动发起外部请求。

于是审查问题从"这段代码正确吗"扩展成"这段代码能碰到什么、会把什么带出去、手上有什么钥匙"。这三个新增面，就是上下文面、动作面、凭证面。缺了它们，六道闸守得再严，也只覆盖了"代码质量"这一维。

## 二、上下文面：会话、路径和工具入参是一整块可外带的数据

依赖包外带数据要靠自己打网络请求，插件不用：它本来就在一条会往外发东西的链路上。所以这一面的第一个检查项不是"它有没有网络代码"，而是"它发出的请求里，哪些字段来自会话"。

我们要求插件在接入前提交一份出站声明，字段固定六项：请求目标域名、HTTP 方法、请求体字段列表、每个字段的来源（用户显式输入 / 会话历史 / 本地文件内容 / 环境变量 / 工具调用返回值）、是否整段随行还是仅结构化摘要、数据落地的地区与保留时长。写不全的插件按不可审阅处理。

三类数据最容易被忽略，也最敏感：

1. **会话历史。** 很多插件把"上下文"当作一个字符串参数原样带上，而上下文里可能包含上一轮粘贴的报错日志、配置文件片段甚至误贴的密钥。
2. **文件路径与仓库结构。** 内部系统的绝对路径、目录命名、分支名本身就是侦察信息，对做工业软件的客户尤其敏感，路径里常常带项目代号。
3. **工具调用的入参与返回值。** 插件读取本轮工具结果"是常见写法，而这个结果可能是数据库查询的行集或工单正文。

真正的攻击路径不一定需要恶意代码。智能体从网页或文档里读到的内容可能带有指令，诱导它把会话内容拼进后续调用——这叫间接提示注入，防护不靠模型自觉，靠结构：会话内容进入出站请求前必须经过字段级脱敏（密钥形态、内部主机名、个人信息形态三类规则），外发目标走按插件粒度配置的白名单，默认拒绝。

## 三、动作面与凭证面：可达范围和钥匙的存放位置

动作面问一句就够：这个插件能碰到的最大范围是什么。要看的是它有没有以机器可读的方式声明所需能力（读哪些路径、能不能联网、能调哪些外部工具的哪几个方法），还是干脆继承宿主进程的全部权限。后者是我们不接受的形态——一旦插件被注入指令，它能做的就不是"读一份文件"，而是提交代码、发工单、改外部账号里的配置。

据此设三条硬判据：危险动作必须走人工确认的白名单，且白名单以"动作 + 目标 + 数量上限"三元组表达，不是"允许使用邮件工具"这种粒度；写入类动作按可逆性分级，可撤回的（草稿、评论）可批量确认，不可逆的（删除、支付、对外发送）逐次确认；插件不得自行申请额外权限，权限提升只能由宿主侧配置变更完成并留痕。

凭证面的常见坏味道是三种：把 API Key 写在插件配置里并随仓库提交、放在宿主进程环境变量里被整份读取、共用一个管理员令牌。对应的验收项：密钥不落盘、不进仓库、不出现在日志与错误堆栈里；每把密钥可独立吊销，也就是说签发时就按插件发放专用凭据，而不是把人的凭据借给它；令牌有到期时间，且吊销之后正在运行的任务会被明确中止而不是静默失败。多租户场景要额外确认一件事——插件是否在不同租户之间共享缓存或凭据，这条通常不在文档里，必须问。

## 四、准入清单：把三个面落成可勾选的项

洹拓科技给内部项目和客户交付用的插件准入表如下，判定只允许"通过 / 有条件通过 / 拒绝"三值，且必须写检查方式（看源码、看运行日志、还是仅看文档）。

| 检查项 | 通过时要看到什么 | 典型不通过表现 |
| --- | --- | --- |
| 能力声明可枚举 | 运行前能列出全部所需权限并在界面审阅 | 只有"需要访问文件系统"这类模糊描述 |
| 出站字段来源标注 | 每个外发字段标明来自会话还是用户输入 | 请求体结构不透明，整段上下文随行 |
| 网络出口管控 | 支持按插件设置域名白名单 | 自带任意 HTTP 调用且无域名限制 |
| 危险动作确认 | 写入类动作走人工确认，含目标与上限 | 直接执行外部写操作，无提示 |
| 凭据独立性 | 每插件专用密钥、可单独吊销、有到期 | 复用宿主管理员令牌、密钥进环境变量 |
| 版本与完整性 | 锁定到具体版本或制品哈希，有签名 | 拉取浮动标签，构建产物不可复现 |
| 可禁用不可卸载 | 一键停用且保留数据与配置 | 只能通过删除目录止损，状态丢失 |
| 遥测可关 | 遥测默认关闭或明确开关 | 埋点无法关闭，且未说明上传内容 |

这八条里，前四条属于"插件这一层"新增的，后四条在传统依赖审查里也有，但在插件语境下代价不同：版本浮动意味着今天审过的代码和明天运行的不是同一份，而它又恰好处在能替你动手的位置。

## 五、分层接入与组合风险：两个各自合规的插件能拼出一条外发链路

把插件按能力分三层管理，比逐个评估更有效，因为审批人可以按层固定：第一层完全离线，只处理本地数据、不联网、不写外部系统，由开发负责人自批；第二层允许只读外部数据，例如查询公开文档或调用只读接口，由技术负责人批准；第三层允许写外部动作或持有凭据，必须由安全角色加业务责任人双签，且限定在项目范围内生效。

分层之后仍要单独做一次组合审查，这是最容易漏的一面。设想两个插件各自看都合格：甲把会话内容整理成结构化笔记写到共享工作区，乙负责把工作区同步到外部服务。单看甲，它只做本地写；单看乙，它只同步"用户主动放进去的东西"。串起来，就是一条从模型上下文到外部域名的通路，而且没有任何一个环节需要人工确认。

我们的做法是把数据流画成一张图再检查：以"可读会话内容"的插件为起点，以"可外发网络请求"的插件为终点，检查是否存在两跳之内的路径；存在就在中间插一个必须人工确认的检查点，或者把其中一端降级为只允许访问隔离目录。这张图要在装插件的时候更新，而不是出事之后重建。

## 六、出问题要能取证，以及为什么插件数量不是选型指标

事故复盘时最常发现的是"知道有问题，无法回答当时是什么状态"。要留的四件东西得提前埋：调用记录（时间、插件标识与版本、动作类型、目标、参数摘要哈希，不存明文敏感值）、上下文快照（脱敏后的当轮可见内容）、制品版本与哈希、权限快照（当时授予的能力集合）。四件里缺任意一件，责任划分就只能靠猜。同时确认一个运行开关：能否在不卸载、不清配置的前提下临时禁用单个插件——这是最短的止损路径，很多框架把它做成了删除，代价太高。

最后回到选型。插件数量多是生态繁荣的信号，不是可用性的证据：它同时意味着大量未被同一套标准审过的代码，正处在能读你上下文的位置。真正该当作指标的是四件事——能力声明能否在运行前枚举、版本与制品能否锁定校验、出问题能否精确禁用单点、有没有独立第三方审过它的出站行为。按这四条筛一遍，剩下的插件数量通常少得让人不舒服，但这时你才对"这个插件能替你做什么"有确定答案。
