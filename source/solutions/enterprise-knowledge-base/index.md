## 适合什么情况

- 资料分散：制度、工艺文件、设备手册、售后工单散在网盘、共享文件夹和老师傅脑子里
- 重复问答占人力：新人培训、售后客服、现场检修，同样的问题每天被问很多次
- 答案必须可追溯：合规、质量、工艺类内容不能接受"模型自己编的"

如果你的资料本身残缺或长期不更新，先别做问答——把资料治理好比接模型重要。

## 我们怎么做

**第一步 · 摸底**：清点资料范围、格式、更新责任人，确认高频问题清单。这一步通常就能判断值不值得做。

**第二步 · 数据链路**：文档解析与切片、向量化、权限边界。表格、图纸、扫描件这类非纯文本内容在这里最费功夫，也是效果差异的来源。

**第三步 · 检索与生成**：检索策略（关键词 + 向量混合）、提示词约束、引用溯源，保证每条答案能点回原文出处。

**第四步 · 评估集**：上线前用一批真实问题做标准答案对照，把"能不能用"变成可复现的测试，而不是演示时看着不错。

**第五步 · 部署与运营**：私有化或云上部署、使用埋点、错例回流机制——知识库的价值取决于有没有人持续维护。

## 交付物

| 内容 | 说明 |
| --- | --- |
| 可运行的问答系统 | Web 端，含权限与使用记录 |
| 数据入库流程 | 谁能传、怎么更新、多久生效 |
| 评估集与验证记录 | 上线前对照结果，后续回归用 |
| 部署与运维文档 | 环境、备份、故障处理 |
| 培训 | 面向管理员与业务骨干各一场 |

## 验收看什么

- 高频问题清单里的答案，能否稳定命中并给出原文出处
- 资料更新后，多长时间内新内容可被检索到
- 权限边界是否可靠：不该看到的部门内容确实看不到
- 一线人员是否真的在用（使用记录比任何评价都实在）

## 常见坑

- 一上来就要"什么都能问"：范围越宽，效果越难保证。先选一个部门的高频场景打透。
- 只算模型成本不算人力成本：知识库没有专人维护，半年后就是一堆过期答案。
- 拿演示效果当验收标准：演示问题都是挑好的，要用事先约定的评估集。
